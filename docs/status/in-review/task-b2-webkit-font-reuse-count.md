status: in review: perf-fonts no longer counts WebKit's memory-cache reuse of a Lato preload as a second download (engine run 44460645965, E6).

- Cause: the preload and the @font-face request already match exactly (same URL with no query string, `as="font"`, `type="font/woff2"`, `crossorigin` anonymous, and both requests are same-origin with no Origin header, so the test server's `Vary: Origin` matches). WebKit reuses the finished preload, and in that `Use` case `CachedResourceLoader::requestResource` adds a second Resource Timing entry (`ResourceTiming::fromMemoryCache`) carrying the preload's own network metrics. That is why the CI log showed a second "css" entry with the same 23 KB: it is not a second transfer.
- Test: every engine still needs exactly one preload ("link") entry per weight. Chromium and Firefox still need exactly one entry. WebKit may have one more, only if it comes from the stylesheet, has the preload's size (which must be more than zero) and ends within 1 ms of when the preload's response ended (before the reuse began); a real second download still fails. The spec blocks service workers so the offline first-visit save (a deliberate cached `fetch` of loaded files) can't add a random entry; this was a local Chromium flake.
- No app change was needed. Proof in WebKit comes from the next engine run (the log line now prints `responseEnd` for each entry, and in WebKit `fetchStart` too).
- On hold, not verified in WebKit: Codex asked at 61ad25e whether WebKit copies the preload's `fetchStart` into the reused entry's `startTime`. If it does, the "reuse began after the transfer ended" check would fail with no second download. That can't be settled without real WebKit numbers, so no assertion was changed; the pull request waits for a WebKit run of this branch that logs both entries.
