# Performance budget check

A simple size check for the built website. It estimates how much HTML, JavaScript, and CSS a browser may download when opening each page.

Run after a complete build, using the project’s pinned Node version:

```sh
npm run build
node scripts/perf-budget.mjs dist
```

The check reads every `.html` file in `dist/` and counts:

| Type | Maximum gzip size per page |
| --- | ---: |
| HTML | 40 KiB |
| JavaScript | 200 KiB |
| CSS | 70 KiB |
| Combined HTML + JavaScript + CSS | 300 KiB |

Every limit is in the `BUDGETS` table at the top of `scripts/perf-budget.mjs`. The check counts each page’s HTML, locally linked scripts and stylesheets, Astro island scripts (including hydration helpers), inline module script imports, and their statically imported JavaScript and CSS. A shared file is counted once per page, not once per reference. Query strings do not make duplicate files. All sizes use Node's `zlib.gzipSync`.

The report prints **PASS** or **OVER** for each page and identifies which limit was exceeded. A limit breach, missing local file, invalid build directory, or unsafe file link causes a non-zero exit status. The checker does not change any files.

**Not covered:** images, fonts, third-party downloads, lazy-loaded modules, time spent executing JavaScript, and real network performance. Anatomy model files (such as `.glb` and `.gltf`) are excluded because they have their own separate **3 MB check**. Inline scripts and styles are included in the HTML size rather than counted twice. This is a size guard, not a substitute for browser performance testing.

The limits are starting thresholds. Before making them mandatory in CI, Claude should compare the report with a complete staging build and confirm the thresholds are appropriate. W10 does not change CI or `package.json`.

### Budget per page type

`/play/pillo`, `/play/sudoku`, `/play/crossword` and `/play/word-path` were share landings with no game until each
game moved to its own page (2026-11-17, D-pending). The single game page budget was re-measured then from the real
game pages (heaviest 119.3 KiB plus 10%); it was not a loosening of the same page. Splitting the shared React and flag
code to shrink every page is on the after-launch list.

The heaviest page of each type plus 10%, rounded up to whole KiB. `tests/unit/perf-budget.test.ts` fails the build
check if any built page goes over its type's budget, so a new page has a limit from day one. Each existing page also
keeps its own per-route budget in `tests/unit/build-output.test.ts` (10% over its first measurement).

### Islands that load late (lane 9, 2026-11-17)

Checked every island for `client:visible` / `client:idle`; none was changed, for these reasons:

- Most islands are `client:only`. Astro can't delay those (an island takes exactly one `client:` directive), and
  switching one to a delayable directive means rendering it on the server first, which changes what students without
  JavaScript see.
- The remaining `client:load` islands (sign-in, sign-up, password reset, account settings, break ideas) are the main
  thing on their page and sit at the top of it, so delaying them would only delay the one thing the student came for.
  The preview pages' islands are internal.
- The one change that would matter is the footer's flag button: it is the only reason React (68 KiB of the 87.8 KiB
  floor) loads on pages with no other island, such as about, privacy and the legal pages. Loading the flag form only
  when the footer comes near the screen, keeping the email link as the fallback, needs a change to `SiteFooter.astro`
  and the flag tests, so it is proposed for after launch rather than done here.
